# M-Group v2 WebUI Specification

## Source and approach

The existing `app/webui/` is the visual and information-architecture baseline only. It is copied into `rebuild-v2/webui/` and the legacy JavaScript API behavior has been removed. Keep the useful layout, navigation, dark visual system, and page groupings, but implement all behavior against versioned v2 contracts. Do not import the legacy runtime or reuse legacy endpoint assumptions.

## Locked product/UI decisions carried forward

### Main navigation and admin experience
- Overview/dashboard, Member, Finance, Payments, Vending & Inventory, Cashier, Devices, Audit & Backup, and Settings remain the core sections.
- Admin-facing labels describe operational roles (for example, Terminal Kasir and Pengendali Vending), not chipset, board, MCU, or controller model.
- Device name, MAC address, online/offline status, and last-seen are operational metadata, never authentication factors.
- The WebUI must not claim that simulated data, scanning, reconciliation, provider connectivity, or physical-device actions are real before the API/device integration exists.

### Member and NFC enrollment
- Member ID is generated by the server/database atomically, not typed or edited by an admin.
- The latest UI decision in `docs/WEBUI-CORRECTIONS.md` uses `UID-00001`, incrementing sequentially. Older conflicting format notes must be reconciled before the v2 API contract is frozen.
- The form includes member name, NIK, phone and relevant member profile fields; NIK validation and uniqueness policy are server-enforced.
- NFC enrollment is started by selecting a registered Cashier and pressing Scan. The server creates a timed enrollment session; the Cashier displays “Silakan scan kartu”, then “Silakan masukkan PIN transaksi”. The server validates the PIN and binds the NFC credential. The UI never asks for manual UID entry in the normal flow and never displays/stores a raw PIN.
- Enrollment must expose clear state, timeout, correlation, and audit outcomes.

### Member finance
- Top-up is initiated from the member balance using a plus action and requires amount, unique reference, source/description, and admin confirmation.
- Production top-up must go through the financial core and immutable ledger with authorization, idempotency, atomic balance mutation, audit events, and reversal support. Never update a balance directly in the UI.

### Vending & Inventory
- Each vending machine has exactly five fixed product positions, Product ID 1–5. No “add product” button and no editable slot/servo fields.
- Each machine owns its own five-position catalog and stock; Product ID 1 on one machine is not the same inventory record as Product ID 1 on another machine.
- A dynamic server-populated machine selector displays editable location/display name, stable device name, MAC address, and authenticated heartbeat status. Offline machines remain selectable so admins can inspect the last-known catalog with an explicit offline state.
- Selecting a machine filters all catalog, stock, and editing rows to that machine.
- Each product row supports image upload, product name, price, stock, NFC promotion, and QRIS promotion. Image uploads are limited to 2 MiB and must have server-side file-type/content validation.
- Promotions display 0% and remain inactive until promotion execution is explicitly implemented. QRIS stays inactive until provider integration exists.
- Product-to-position mapping is fixed: Product ID 1 → position/servo 1 through Product ID 5 → position/servo 5.

### Audit, backup, payment and operations
- Payment history supports search and NFC/QRIS channel and status filters.
- Reconciliation summaries distinguish succeeded, pending, failed, and refunded transactions, but must not be represented as real provider reconciliation until connected.
- Only one Admin super-admin account manages the WebUI. Member is a transaction client identity, not a WebUI login account.
- Top-up, payment, vending, refund, and adjustment actions use stable idempotency references and append-only audit/ledger records.

## Clean-room implementation rules

- The copied HTML/CSS is a visual baseline, not evidence that a feature is implemented.
- Legacy `app.js` API calls are not reused. The current v2 WebUI uses `MGroupApiV2` and versioned `/api/v2` endpoints.
- Administrator login uses username/password and a server-side HttpOnly SameSite=Strict session cookie; Admin API Tokens are not accepted by the WebUI.
- The initial super-admin is created at fresh installation from `MGROUP_ADMIN_USERNAME` and `MGROUP_ADMIN_PASSWORD`; password changes are performed inside WebUI Settings using the old password and a twice-entered new password.
- Admin API calls use same-origin cookies and server-side session/RBAC checks. State-changing admin requests validate Origin when supplied.
- Keep the UI responsive and accessible; show loading, empty, success, and error states for each real request.
- No merge to `main` until feature contracts, UI, API, integration tests, security review, and deployment rehearsal are complete.


## Implementation status — source update

The canonical WebUI now includes username/password login, cookie-session restoration after page refresh, explicit logout, password change settings, member Edit and NFC enrollment/replacement actions, product image upload/preview, device management, ledger/transaction/audit views, and backup/restore controls. These are source-level implementations wired to v2 endpoints; their presence is not a claim of completed browser or end-to-end acceptance. Automated tests, full API contract coverage, firmware compilation, physical NFC and vending tests, and backup/restore rehearsal remain required before release.


## Simplified actors and deferred features

- Exactly two actor categories exist: **Admin** (one super-admin account, also the WebUI administrator) and **Member** (client identity for NFC transactions).
- No operator, teller, auditor, or additional WebUI admin roles exist. Their accounts, screens, APIs, schema fields, PINs, and authorization branches are removed.
- Each Member receives a sequential server-generated UID (`UID-00001`, `UID-00002`, ...). Allocation is atomic in a database write transaction; Admin cannot type or edit it.
- Cashier payment and top-up verify the Member PIN. No operator identity or operator PIN is required.
- Cashier configuration stores only its settlement-account binding; device authentication remains based on Device Key.
- Pertamini and loan features are deferred and excluded from active navigation and runtime scope.
